# 🎵 Music Data Processing Practice

음악 스트리밍 서비스에서 자주 마주치는 데이터 처리 문제를 **순수 Java로 직접 구현**하고, 단순히 동작하는 코드를 만드는 데서 끝나지 않고 **"왜 이 구조와 자료구조를 선택했는가"** 를 설명할 수 있도록 설계 근거를 함께 기록하는 저장소입니다.

실제 음악 서비스 백엔드에서 발생할 수 있는 재생 로그 처리, 중복 재생 제거, 정산용 재생 집계, 실시간 차트 Top-N, 최근 재생 목록, 대용량 파일 처리 문제를 작은 단위로 나누어 직접 구현합니다.

초기 구현은 외부 인프라 없이 Java만 사용합니다. 이후 각 문제를 실제 서비스 규모로 확장한다면 Kafka, Redis, Spring Batch, DB 등을 어떤 위치에 적용할 수 있는지도 별도로 정리합니다.

---

## 🎯 목적

이 저장소의 목표는 특정 프레임워크 사용법을 익히는 것이 아니라, **데이터 처리 문제 자체를 이해하고 직접 해결하는 능력**을 훈련하는 것입니다.

주요 목표는 다음과 같습니다.

* 음악 재생 로그를 직접 읽고 처리한다.
* 대용량 입력을 메모리에 모두 적재하지 않고 처리한다.
* 재생 인정 기준과 어뷰징 판정 규칙을 구현한다.
* 곡별 / 사용자별 데이터를 집계한다.
* Top-N 문제를 여러 방식으로 구현하고 비교한다.
* 최근 재생 목록과 같은 상태 기반 문제를 구현한다.
* 시간 복잡도와 공간 복잡도를 직접 분석한다.
* 같은 문제를 해결할 수 있는 여러 방법을 비교한다.
* 구현한 코드의 구조적 선택 이유를 설명할 수 있도록 기록한다.
* 로컬 단일 프로세스 구현이 실서비스에서 어떻게 확장되는지 연결해서 생각한다.

이 저장소에서는 특히 다음 질문에 답할 수 있는 상태를 목표로 합니다.

> 왜 이 자료구조를 사용했는가?

> 데이터가 100배 증가하면 어디에서 문제가 발생하는가?

> 메모리가 충분하지 않다면 어떻게 처리할 것인가?

> 현재 구조 대신 다른 방법을 선택할 수 있었는가?

> 실서비스에서는 Kafka, Redis, DB를 어디에 적용할 수 있는가?

# 🧱 경계를 이렇게 나눈 이유

## `domain`

비즈니스 규칙을 관리합니다.

예를 들어 다음과 같은 규칙이 포함될 수 있습니다.

```text
30초 이상 재생한 경우만 유효 재생으로 인정
```

```text
동일 사용자가 동일 곡을 60초 이내 반복 재생한 경우 중복 처리
```

이러한 규칙은 파일 읽기나 데이터 집계 방식과 독립적으로 변경될 수 있습니다.

예를 들어 재생 인정 기준이

```text
30초
```

에서

```text
60초
```

로 변경되더라도 집계 알고리즘 자체는 수정하지 않는 것을 목표로 합니다.

---

## `reader`

입력 데이터를 읽고 파싱하는 책임을 가집니다.

예를 들어 CSV 파일을 다음과 같이 처리합니다.

```text
File
 ↓
BufferedReader
 ↓
한 줄 읽기
 ↓
Parsing
 ↓
PlayEvent
```

입력 파일 전체를 `List`에 저장하지 않습니다.

현재는 파일 입력만 사용하기 때문에 처음부터 불필요한 인터페이스 계층을 만들지 않습니다.

향후 실제로 다른 입력 소스가 추가될 필요가 생긴다면 그 시점에 추상화를 검토합니다.

예:

```text
File
Kafka
HTTP
Database
```

---

## `aggregator`

데이터 집계 알고리즘을 담당합니다.

예:

```text
곡별 재생 횟수
사용자별 재생 횟수
Top-N
```

집계 코드 내부에는 다음과 같은 비즈니스 규칙을 직접 작성하지 않는 것을 원칙으로 합니다.

```java
if (duration >= 30000) {
    ...
}
```

이런 규칙은 `domain` 쪽에서 처리합니다.

---

## `writer`

처리 결과 출력만 담당합니다.

예:

```text
Console
CSV
JSON
```

출력 방식이 변경되더라도 집계 로직은 수정하지 않는 것을 목표로 합니다.

# 🚫 과설계를 피하는 기준

이 프로젝트는 Clean Architecture나 DDD를 연습하기 위한 프로젝트이기도 하지만, 패턴 자체를 적용하는 것이 목적은 아닙니다.

다음 기준을 적용합니다.

* 구현체가 하나뿐이라면 무조건 인터페이스를 만들지 않는다.
* 실제 변경 가능성이 확인되지 않은 부분은 추상화하지 않는다.
* 레이어는 **변경 이유가 다른 부분**을 중심으로 분리한다.
* 현재 문제를 해결하는 데 필요하지 않은 기술은 추가하지 않는다.
* 패턴 이름보다 코드가 해결하려는 문제를 우선한다.

예를 들어 초기에는 다음과 같은 구조를 만들지 않을 수 있습니다.

```text
PlayEventReader
    ↑
CsvPlayEventReader
```

CSV Reader 하나밖에 없다면 먼저 단순 구현으로 시작합니다.

두 번째 구현체가 실제로 필요해졌을 때 인터페이스 추출을 검토합니다.

# 📄 입력 데이터 형식

기본 재생 이벤트는 다음과 같은 형식을 사용합니다.

```csv
eventId,userId,songId,playedAt,durationMs
e-0001,u-100,s-2001,2026-09-24T10:00:00,185000
e-0002,u-101,s-2001,2026-09-24T10:00:04,25000
e-0003,u-100,s-2002,2026-09-24T10:00:10,210000
```

각 필드 의미는 다음과 같습니다.

| 필드           | 설명           |
| ------------ | ------------ |
| `eventId`    | 재생 이벤트 식별자   |
| `userId`     | 사용자 식별자      |
| `songId`     | 음악 식별자       |
| `playedAt`   | 재생 이벤트 발생 시각 |
| `durationMs` | 실제 재생 시간(ms) |

문제별로 필요한 경우 입력 데이터는 추가될 수 있습니다.

# 📏 공통 설계 원칙

## 1. 입력 크기를 가정하지 않는다

가능한 경우 파일 전체를 메모리에 올리지 않습니다.

다음 방식은 피합니다.

```java
Files.readAllLines(...)
```

대신 입력을 순차 처리합니다.

```text
한 줄 읽기
 ↓
파싱
 ↓
처리
 ↓
다음 줄
```

---

## 2. 비즈니스 규칙은 `domain`에 둔다

예를 들어 아래 숫자를 집계 코드에 직접 작성하지 않습니다.

```java
30000
```

대신 의미가 드러나는 정책으로 표현합니다.

```text
ValidPlayPolicy
```

---

## 3. 잘못된 입력 하나로 전체 처리를 중단하지 않는다

파싱 실패 레코드는 별도로 계산하고 가능한 경우 나머지 데이터는 계속 처리합니다.

예:

```text
총 입력        1,000,000
정상 처리        999,950
파싱 실패             50
```

---

## 4. 시간 / 공간 복잡도를 기록한다

각 문제 README에 아래 내용을 작성합니다.

```text
시간 복잡도

O(N)
```

```text
공간 복잡도

O(U)
```

여기서 `U`는 고유 데이터 개수를 의미할 수 있습니다.

---

## 5. 테스트는 경계값부터 작성한다

정상적인 데이터만 테스트하지 않습니다.

예:

```text

```

이라면 최소 다음을 테스트합니다.

```text
29.999초
30초
30.001초
```

다음과 같은 경우도 포함합니다.

* 빈 입력
* 잘못된 입력
* 동일 타임스탬프
* 동일 사용자
* 동일 곡
* 중복 이벤트
* 데이터 1건
* Top-N보다 데이터가 적은 경우

# 🕘 최근 재생 목록

최근 재생 문제에서는 먼저 다음 정책을 결정합니다.

예:

```text
A → B → C → A
```

중복을 제거한다면:

```text
A
C
B
```

중복을 허용한다면:

```text
A
C
B
A
```

따라서 문제를 풀기 전에 아래 내용을 명확하게 정의합니다.

* 같은 곡 중복 허용 여부
* 최근 목록 최대 크기
* 시간 기준 정렬 여부
* 동일 시각 이벤트 처리 기준

# 📊 Top-N

Top-N 문제에서는 최소 두 가지 구현을 비교합니다.

## 전체 정렬

```text
모든 데이터 집계
 ↓
전체 정렬
 ↓
상위 K개 반환
```

시간 복잡도:

```text
O(N log N)
```

장점:

* 구현이 단순하다.
* 데이터가 작으면 충분히 효율적이다.

단점:

* 데이터가 커지면 불필요하게 전체 데이터를 정렬한다.

---

## 크기 K Heap

```text
데이터 순회
 ↓
크기 K PriorityQueue 유지
 ↓
Top K 반환
```

시간 복잡도:

```text
O(N log K)
```

장점:

* `K << N`인 경우 효율적이다.
* 전체 데이터를 정렬할 필요가 없다.

단점:

* 구현이 조금 더 복잡하다.
* 데이터가 작으면 전체 정렬과 체감 차이가 거의 없을 수 있다.

따라서 단순히 더 빠른 방법을 선택하는 것이 아니라 **입력 규모와 코드 복잡도를 함께 고려**합니다.

---

# 💾 메모리보다 큰 데이터 처리

최종 단계에서는 입력 데이터 또는 집계 상태가 JVM Heap보다 큰 상황을 가정합니다.

예:

```text
입력 데이터: 100GB

사용 가능한 Heap: 1GB
```

이 경우 모든 데이터를 메모리의 `Map`에 유지할 수 없습니다.

다음과 같은 방식을 연습합니다.

```text
Input File
    ↓
Hash Partition
    ↓
Temporary Files
    ↓
Partial Aggregation
    ↓
Merge
    ↓
Final Result
```

즉,

```text

→ 최종 병합
```

* 임시 파일 관리

* Hash 분포
* 메모리 제한
* 처리 시간과 공간 사용량의 트레이드오프

# 🧭 실서비스 확장 시나리오

# ✅ 진행 원칙

* 첫 구현은 가능한 한 직접 한다.
* 막힌 부분은 `NOTES.md`에 기록한다.
* 애매한 요구사항은 구현 전에 가정부터 정의한다.
* 동작하는 코드보다 설명 가능한 코드를 우선한다.
* 과도한 추상화와 패턴 적용을 피한다.
* 입력 데이터가 커지는 상황을 항상 생각한다.
* 자료구조를 선택했다면 이유를 설명할 수 있어야 한다.
* 복잡도를 직접 계산한다.
* 테스트는 정상 케이스보다 경계값을 중요하게 본다.
* AI 리뷰 결과를 무조건 적용하지 않는다.
* 실서비스 기술을 사용하기 전에 순수 Java로 문제의 본질부터 이해한다.
* **설명할 수 없는 코드는 넣지 않는다.**
